## Remaining harness concerns

1. **The baseline was measured at a pinned commit.** `evals/baseline.json` now holds P2's
   runs at `d3373d0`, the condition both retros used. The next retro should first
   re-baseline at its own HEAD (the exclusion now makes that safe) to measure drift.
2. **Ceiling and overfitting.** The target is now at 20/20 on a single Pattern D scenario,
   and P2 was shaped by that scenario's failures. Add more Pattern D variants (another
   kind of constraint, an owner who can't be reached, the assistant itself building the
   workaround), plus a negative where an alternative channel is the right first answer.
   That checks the "do not propose alternatives" wording doesn't over-reach.
3. **Coarse checks off target.** Non-target scenarios run 3 times, where the rule only
   counts a drop of 2 or more. A one-run regression elsewhere would not register.
4. **Classifier.** `classification` judges trigger and pattern only, so a run that
   triggers correctly but proposes a fix first is still labelled `c_pass` (retro 1,
   candidate runs 8 and 11). The violation and first-action columns catch it; the class
   label does not.
5. **One judge.** The grader is the same model family as the subject, with no human
   spot-check beyond reading the violating runs. The judge agreed with the literal
   "SPIRAL CHECK" match on every run, but first-action and violation calls are the
   judge's alone.
6. **Two ways to load.** CLAUDE.md's Debugging rule names `SKILL.md`, so a subject can
   load the skill without the description triggering it (1 of P2's 20 target runs did).
   Trigger rates therefore measure description plus CLAUDE.md together.
